04Methodology

The single hardest design decision in the project was making the contest actually fair. A rate-based contest sounds fair on paper, but pitting a 200-transaction store against a 600-transaction store turns it into two different sports. A two-stage Swiss system solves it.

Week 1: The Seeding Round

With no prior performance data to reference, stores are seeded by transactions per cashier, a single metric that normalizes for both traffic and staffing. A small store running hot lands near a big store running slow, and adjacent stores in the seed list pair off.

This is the only week rate isn't the driver. Every subsequent week uses live data.

Weeks 2 – 5: Swiss Rounds

Stores re-pair every week by closest cumulative WTD conversion rate, the same logic a chess Swiss tournament uses. The leader plays the runner-up, third plays fourth, and the pattern continues down the table.

A greedy algorithm walks the ranked list and prefers no rematches. If the closest opponent has already been faced, it skips to the next-nearest unpaired peer. Rematches only happen when nothing else is available.

The pairing function lives inline next to the data model, with no service or schedule file behind it. Pairings are derived from the same numbers everything else uses.

// Stores ordered by cumulative WTD rate, tiebreak by txns-per-cashier
function rankStoresThrough(weekIdx) { ... }

// Greedy walk: closest unpaired opponent that hasn't been faced before
function generatePairings(weekIdx) {
  if (PAIRINGS_CACHE[weekIdx]) return PAIRINGS_CACHE[weekIdx];
  const prior = new Set();
  for (let i = 0; i < weekIdx; i++) {
    generatePairings(i).forEach(([a, b]) => prior.add(_pairKey(a, b)));
  }
  const pairs = _pairOrdered(_orderForWeek(weekIdx), prior);
  PAIRINGS_CACHE[weekIdx] = pairs;
  return pairs;
}

The contest's truth lives in the per-store weekly numbers, and everything else on the page is a pure function of that object. There's no separate schedule file to keep in sync, no manually-maintained leaderboard, and no "did I update both places?" risk built into the workflow.

Each Monday, the operator opens the file, pastes new numbers into the data block, and saves. A refresh is all it takes.

07Responsive

The tracker is consumed on a leadership iPad more often than on a phone, but it has to feel native on both. Four breakpoints, three layout modes, and one component set carry it from a phone in the back room to a 4K display in the boardroom.

BreakpointDeviceLayout
≤ 639px Phone Single-column stack. Header stats wrap to two rows. Match cards full width with vertical winner/loser stacking.
640–959px Tablet portrait Content rail centered at 740px max-width. Header stats compress to a 3-column grid. Season strip still scrolls horizontally if needed.
960–1399px iPad landscape / desktop Two-panel grid. District overview (wide) + week banner (tight) side-by-side. Match cards in a 2-column grid. Store breakdown 2-up. Pairings strip stretches edge to edge.
≥ 1400px Boardroom / wide desktop Rail widens to 1360px. Match cards drop into a 3-column grid so all six pairings fit above the fold on a 16:10 display.

The layout favors density over decoration, so every breakpoint maximizes the information visible above the fold. The header marquee, season strip, and district overview are deliberately short so the matchups always sit close to the top.

08Stack

The whole tracker is one HTML file, about 3,000 lines including embedded CSS and JS. There's no build step, no framework, no package manager, and no deploy script. The site can be emailed.

The constraint is deliberate. Internal tools that ship to non-technical operators survive longer when there's less surface area for things to break: no node_modules to update, no SSL cert to renew, and no CMS to lock anyone out of.

To preview locally, the operator runs python3 -m http.server 8000 in the project folder. To deploy, the file gets dropped into any static host, or just shared as an email attachment.

The trade-off is that there's no live data. Each Monday, a person opens the file, pastes new numbers into the JavaScript object, and saves. That workflow is a feature, not a bug: it keeps an audit trail, and it keeps the file portable.

The visual identity, the methodology, and the algorithms all live in the same place. If a designer wants to tweak the gold value, it's a single find-and-replace. If a district lead wants to extend the contest to seven stores, the pairings code already handles odd-count rosters with byes.
